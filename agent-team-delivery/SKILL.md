# 團隊制交付 · Orchestrator + Peers

> 一個忠實模擬了可利用產品的重放器,不會偵測到那個漏洞——它只會替漏洞背書。
> 驗證的價值不在於「我看過了」,而在於「我讓它紅過一次」。

## 這個 skill 什麼時候用

當工作量大到一個 session 做不完、或需要同時推進互相依賴的幾條線時。
**不要為了「看起來平行」而開 agent。** 每個新 session 都是冷啟動,要重新建立
脈絡;只有當一條線可以獨立進行到「可交付」為止,才值得分出去。

---

## 一、角色與所有權

| 角色 | 負責 | 絕不做 |
|---|---|---|
| **Orchestrator** | 定優先序、開 issue、派工、**獨立驗證**、merge & push、對 owner 報告 | 自己動手實作(會失去驗證的獨立性) |
| **Peer**(FE/BE/writer/…) | 在自己的分支與 worktree 上實作、自測、寫 guard、交付 | 自己 merge 進 main;解不是自己造成的衝突 |

**檔案有主。** 每個檔案屬於某一個 peer。跨界修改**可以**,但必須在交付訊息裡
主動點名,由 orchestrator 轉給檔案的主人裁決。**最糟的情況不是衝突,是兩邊
安靜地各自持有一份不同的真相。**

**Orchestrator 不寫產品程式碼。** 一旦寫了,後面就是自己驗自己——這是本
skill 想避免的第一件事。寫探針、寫破壞測試、寫驗證腳本可以;那不是產品。

**如果你在切換角色之前就已經寫過產品程式碼**(常見:你先做了 phase 1,才
決定改當 orchestrator),不要假裝沒發生:

1. **主動申報**,對 owner 也對 peer。
2. 把那部分當成**全系統驗證最少的地方**,而不是最可信的——它沒有經過任何
   獨立的眼睛。
3. 明確告訴 peer:「**如果你在那段程式碼裡找到缺陷,先假設是我錯,不是你
   錯。**」否則他們會繞過去,而不是回報。

真實案例:文件、實作、測試三份都出自同一個腦袋,於是三份**一致地錯**。它
之所以被抓到,只因為驗收 harness 是從設計文件的另一段獨立敘述期望值。

## 二、派工:一份好的 brief 長什麼樣

派工不是轉貼 issue 標題。一份能讓 peer 一次做對的 brief 有五塊:

1. **裁決(ruling)與它的理由。** owner 說了什麼、為什麼。peer 會遇到你沒
   想到的取捨,它需要知道判準才能自己決定。
2. **不可協商的約束**,而且要說明「錯了會怎樣」。
   例:「這個閘門必須 fail open——取不到資料時要**顯示**按鈕。隱藏會把一筆
   真實紀錄無聲丟掉,玩家永遠不知道。被拒絕可以再來,沒被提供不行。」
3. **明確不要做的事**,以及邊界在哪。
4. **要怎麼證偽**——指定那個「會咬人」的案例。
   例:「證偽案例必須在第一個元素平手、在後面的元素分勝負;若在第一個元素
   就分出高下,錯誤的實作也會通過,等於沒證明任何事。」
5. **遇到什麼情況要停下來問我**,而不是自己想辦法繞過。

### 一定要寫進去的一句話

> 如果做不到 X,**回報我,不要自己降規格**。

縮小範圍是 owner 的決定,不是 peer 的。這一句話在真實專案裡救回過一次
設計意圖被安靜推翻的情況(五張牌塞不下時,peer 沒有偷偷把牌縮小,而是
帶著實測數字上報,由 owner 裁決)。

### 但這句話一定要配一份「你可以自己做什麼」

**只講「有事回報我」而不講授權範圍,peer 會卡在一個永遠不會到的確認上。**

真實案例:一個 peer 完成並通過驗證之後,停了一小時沒有 push。它不是在等我
——**它去問了 owner**。因為從它的 session 內部看,那個人類才是它的使用者,
我只是一個外部訊息來源。我花了一小時診斷它「卡住」,實際上它在等一個我
根本不知道存在的確認。

所以 brief 裡要有三欄,而且要寫死:

| | 例子 |
|---|---|
| **不必問,直接做** | 我已確認驗證通過的東西;自己區域內、能維持測試全綠的修正 |
| **先問 orchestrator** | 跨進別人的區域;更動設計文件裡的數值;會讓 guard 變紅的改動 |
| **不要問 owner** | 一律走 orchestrator。你握有全局脈絡,而且只有你能同時碰到所有 peer |

最後一列特別重要:**peer 之間通常沒有通道,只有 orchestrator 有。** 所以
「你去跟 FE 談好」這種指示是**無法執行的**——我下過一次,對方就地卡住,而
那看起來跟「它掛了」一模一樣。需要另一個 peer 的決定,一律由你居中轉。

**這三欄必須寫在第一份 brief 裡,不能等到出事再補。**

我第一次漏掉時,BE 卡了一小時去問 owner。我補了授權給 BE,**然後 FE 一小時
後做了一模一樣的事**——因為 FE 的 brief 也漏了同一欄,而我的更正是**逐一
發的**,補了一個不會補到另一個。

兩件事讓「事後補」永遠來不及:

1. **你發現對方被擋住的時候,它已經去問過人了。** 授權是為了讓那次詢問不
   發生,補在後面只能救下一次。
2. **這是 per-peer 的洞。** 每一個沒拿到那三欄的 peer 都會各自踩一次,而且
   症狀完全相同(安靜、無進度、看起來像當機),你會重新診斷一次。

所以它屬於**派工樣板**,跟「回報我,不要自己降規格」那句話並排——那句講
**什麼時候要停下來**,這三欄講**什麼時候不必停**。只給前者,peer 會停在
所有地方。

## 三、交付:一份好的 handover 長什麼樣

要求每個 peer 用固定格式回報:

```
分支 / SHA / base(是否已 rebase 到最新 main)
測試結果(數字,不是「通過」)
證偽:我讓哪一條 guard 紅過?紅的時候它說了什麼?
我改了什麼不屬於我的檔案
我沒有驗到的部分(以及為什麼)
```

**「我沒有驗到的部分」是最有價值的一欄。** 它決定 orchestrator 要親手做
什麼。真實例子:BE 明講「binding 在 isolate 裡解析、D1 的行為、路由——
這三件事部署前無法測」,那就正好是 orchestrator 部署後唯一該做的事。

---

### 回程:不要要求宣告,要製造痕跡

「做完回報我」是一個**需要雙向通道**的設計,而通道**兩端都可能在睡**。
5.11 講的是去程會安靜地失敗;回程一樣會,而且多一個問題:

> **peer 可能根本找不到你的位址。** 當前 session 通常會被自己的 session
> 列表排除——你查不到自己是誰,也就給不出回信地址。你寫「done 之後告訴
> 我」的時候,可能從來沒有存在過一條回信的路。

改成**單向拉取**。要求 peer 留下痕跡,而不是送出通知:

| 要求 peer 做的 | orchestrator 怎麼看到 |
|---|---|
| 在 issue 留言(帶那五行) | `gh issue list` / `gh api .../comments` |
| push 到分支或 main | `git fetch` |
| 開 PR | `gh pr list` |

三個都不需要通道活著、不需要對方醒著,也不需要你醒著。

### 再讓痕跡叫醒你

痕跡解決了「看得到」,沒解決「什麼時候去看」。放一個**背景哨兵**:

```
baseline = 快照(origin/main、各分支 SHA、各 issue 留言數、issue 狀態)
每 N 秒重新快照;和 baseline 不同就:
    印出 diff
    印出新留言的「內容」,不只是數量
    exit 0
設一個死線(例如一小時),到了就結束,讓上層重放
```

關鍵不是輪詢,是**它在有事發生的那一刻結束**——而一個結束的背景任務會**自動
重新叫起 orchestrator**。於是輪詢變成事件觸發,而且完全不依賴 peer 的合作。

哨兵結束時要把**新留言的內容一起印出來**。否則你醒來只知道「有事發生」,還
得再花一輪去問發生了什麼。

**分清楚「完成訊號」和「活動」。** 第一版哨兵我把 peer 的功能分支也列進觸發
條件,結果它在對方每一個 work-in-progress commit 上都把我叫醒——那是「他正在
打字」,不是「他做完了」。

| | 例子 | 該不該叫醒你 |
|---|---|---|
| 完成訊號 | issue 留言、push 到 main、開 PR、issue 關閉 | **會** |
| 活動 | 功能分支上多了一個 commit | 不會,但**觸發時一起印出來當脈絡** |

判準:**這個訊號是 peer 「刻意發出」的,還是它工作時「順手留下」的?** 只有
刻意發出的才算交付。

## 四、驗證:orchestrator 的核心工作

### 4.1 從乾淨的、抽離的 worktree 驗

```bash
git worktree add --detach <tmp> <明確的 SHA>
```

**不要在 peer 的工作目錄驗。** 它有未提交的檔案,你會量到不是它交付的東西;
更糟的是你可能把它的東西一起 commit 掉。

**detached worktree 還有一個附帶好處**:它不能 push,所以不會誤觸生產線。

### 4.2 驗證 = 讓它紅一次

**看過程式碼不算驗證。跑過測試也不算。** 唯一算數的是:

> 我把產品弄壞,那條 guard 有沒有紅?紅的時候它說的話對不對?

破壞要下在**產品**上,不是在 fixture 上。對著手寫的假資料弄紅一條測試,
證明不了那條測試能保護真的程式碼。

每次修改 guard 之後,**證偽要重跑**。改過的 guard 不再享有先前那次證偽的
背書。

### 4.3 A/B 是最強的證據

同一支探針、同一個方法,只換 build:

```
                  修正前          修正後
記錄的動作         0 → 1          0 → 0
eventRng      2567497118 → 104095635   不變
```

兩邊都跑在真正的產品上,差異只有那一個 commit。這比任何測試報告都難以爭辯。

### 4.4 眼睛是不可替代的儀器

**測試會驅動引擎,但沒有人把畫面畫出來。** 在真實專案裡:280 個測試 + 大量
機器人跑分,照樣讓結算畫面印出三句假話;399 個測試,照樣讓標題和統計列擠
在一起沒有間隔。

所以:**凡是「存在目的就是被人看」的頁面,先打開看,再跑套件。**
而且要有能力回答「我現在看到的,是我剛才 ship 的那一份嗎?」(見 5.1)。

---

### 4.5 先寫驗收,再等實作

在 peer 交付**之前**就把驗收標準寫成會跑的檢查。這不只是為了快——**實作還
不存在的時候,你的期望值不可能被它污染**(見 5.2)。

三件事讓它真的獨立:

- 常數從**設計文件抄寫**、寫死在 harness 裡,不從產品的設定檔讀。
- **先拿產品的設定去對這些常數**。這樣「改產品裡的數字來讓行為測試通過」
  會在對照那一關就爆,而不是安靜地通過。
- 用**三態**:通過 / 失敗 / **尚未實作**。把「還沒做」和「做了但錯」混成
  同一種紅色,一整張 issue 可以在功能不存在的情況下被標記成完成。

harness 由 orchestrator 所有。peer 可以跑,但不編輯——某一列錯了要回報,
由你修。

## 五、失敗目錄:儀器自己會騙人

這一節是本 skill 最貴的部分。以下每一條都真的發生過,而且**都是在很用心
工作的時候發生的**。

### 5.1 舊的快取 / 舊的 origin

有 service worker 的站台,快取優先的 shell 會在你以為在看新版時餵你舊版。
加 query string **不一定**能穿過(cache 可能 `ignoreSearch`)。

- 驗改過的 JS/CSS,要用**全新的 origin**(換 port),不是重新整理。
- 在瀏覽器裡量任何東西之前,先讀一個**版本戳記**(例:`window.__build`),
  跟你剛 ship 的比對。
- `curl` 沒有 service worker,是判斷「origin 到底送出什麼」的裁判。

> 同一個 session 裡,我先正確地把一個異常數字診斷成「舊快取」,二十分鐘後
> 又在同一個瀏覽器上量另一個頁面,完全沒想到要套用同一條。
> **診斷出一個陷阱,不等於下一次會避開它。**

### 5.2 檢查從被檢查的東西身上取得期望值

最常見、最難看見的一種假綠。

- 從 INSERT 語句取出欄位清單,再用同一份清單讀回來 → 把兩個欄位對調會
  **互相抵銷**,測試沉默通過。
- 期望值由被測資料推導 → 你測的是資料的形狀,不是規則。

**判準:如果我把規則改錯,期望值會不會跟著一起錯?** 會的話,這條檢查沒有用。
期望值要另外手寫、獨立敘述那條規則。

### 5.3 在能運作的區間驗證儀器

我曾用「這一欄完全線性」來證明我的量測方法可靠——但**線性的那一欄是溢出
的區間,而故障只存在於「裝得下」的區間**(`min-height:100vh` 讓任何裝得下
的頁面都回報 0)。

> 在能運作的那一半驗證儀器,對壞掉的那一半什麼也沒說。

**判準:提出一個驗證時,先說出它取樣了哪個區間、總共有哪些區間。**
只要路徑上有任何「飽和 / 夾限 / 釘死」的機制,它造成的邊界**就是**區間分界。

### 5.4 一句正確的話,配上錯誤的適用範圍

測量是真的,句子是真的,**範圍是錯的**。因為測量真實,結論就感覺理所當然,
而且從句子內部看不出來。

例:「這個檢查不再能證明 SQL 字串一致」——真的,但讀者會自己補上一個
比事實大得多的範圍,然後去「修復」一個更好的設計。

**解法(適用於任何有界的主張,不只註解):**
> 在同一段話裡同時寫下「還證明得了什麼」和「不再證明什麼」。
> 光寫否定句,讀者會自己補上界線,而且補得比事實大。

這條同樣適用於 commit message、交接、issue 留言,以及 orchestrator 的
驗證報告——**「我沒驗到 X」如果不配上「我驗到了什麼」,一樣會誤導。**

### 5.5 名字承諾得比斷言多

測試叫「a wall move costs nothing, **and a legal one still costs a turn**」,
但合法那半只斷言了位置、記錄、事件,**從來沒有斷言回合**。
稽核覆蓋率的人讀名字、打勾、不會打開內容。

**要嘛補斷言,要嘛改名字。**

### 5.6 對缺席的主張,要先證明現場非空

「按了牆壁什麼都沒發生」——如果當下**沒有牆可以按**,這條測試永遠通過。

```js
assert(walls().length > 0, "沒有牆可撞,這條 guard 從來沒有試過");
```

任何「必須不包含 / 必須沒有改變」的檢查,都要先斷言它讀取的區域非空。

### 5.7 合成事件不是真的互動

- `el.click()` 送出 `detail: 0`,那是 **Enter 鍵**的簽名,不是滑鼠點擊。
- 合成的 tap 不會產生 hover,所以用它做的 guard 對 `:hover` 分支毫無證據力。

### 5.8 隱藏 / 不合成的 pane

計時器被節流、有限動畫永遠不會結束(`await animation.finished` 因此永不
解析)、`innerWidth` 讀到 0。症狀是「跑很久像當掉」或「一堆莫名其妙的失敗」。

**而且解法本身會製造新的假失敗**:我裝了一個每 100ms 送 keydown 的
「解卡幫浦」,結果它把正在斷言「必須等待玩家按鍵」的測試全部弄紅。

### 5.9 量到容器,而不是量到東西本身

- 縮放自適應的元素,量它自己的 rect,永遠回答「放得下」。要量**容器**。
- 從靜態 HTML 推算高度,會漏掉 **JS 載入後才掛上的元素**(一個語言切換鈕
  就值 69px,足以讓兩份仔細的量測差出一整個結論)。

### 5.10 pipe 吃掉 exit code

```bash
cmd | grep FAIL; echo $?      # 這是 grep 的狀態,不是 cmd 的
cmd > /tmp/out.txt; echo $?   # 這才是
```

---

### 5.11 派工回報成功,不代表對方收到

**整份 skill 假設派工會到。它不一定會到。**

通常有兩條通道,而它們的行為完全不同:

| 通道 | 送到哪裡 | 對方沒在跑的時候 |
|---|---|---|
| peer 訊息 / agent 佇列 | 對方的 **agent loop** | **永遠不會排空**,訊息不會出現在它的 transcript |
| session 訊息 | 以**使用者回合**送達 | 會喚醒 interactive session |

`success: true` 常常只代表**名字解析到一個可達的 agent**,不代表送達。

而且這個陷阱**自帶一個假的證偽**:拿一個不存在的名字去送、被拒絕,看起來
像是證明了通道會動。它只證明了**位址解析**。這正是 5.4——一句正確的話,
配上比事實大的適用範圍。

**判準,兩個都要:**

1. 先看對方的 **`isRunning`**。沒在跑的 session 不會處理任何東西。
2. 派工之後,**去對方的 transcript 搜尋你自己訊息裡的一個特徵字串**。搜不
   到就是沒送到,不管回報說什麼。

**在確認送達之前,不要開始等。** 真實案例:九則訊息、兩小時、三次「他們
開工了嗎」的檢查,全部在一條靜默不送達的通道上;`isRunning: false` 從第一
分鐘就在那裡,只是沒有人去看。

**回程有同樣的病,解法在三之「回程」**:不要要求 peer 宣告,要求它留下痕跡,
再放一個哨兵把痕跡變成叫醒你的事件。

### 5.12 取樣要取「能分辨的點」,不是方便的點

設計文件會自己跟自己矛盾——同一節裡同時寫著一條**公式**和一張**表格**,
而兩者只在某些點上不同。

真實案例:一份設計文件同時寫著一條乘數公式和一張三列的對照表。兩者在**前
兩列給出相同的答案**,只有第三列(區間的一端)不同。於是三列裡有**兩列替
錯誤的公式背書**,而它活過了兩個版本的設計文件——每個讀過的人都抽樣過,
只是都抽在一致的那兩點上。

> 在方便的點取樣,會**確認**一個 bug。

**先問:哪些點能分辨這兩種解釋?只在那裡取樣。** 而且當文件裡有 N 個地方
描述同一件事,不要挑一個信——**全部列出來,看誰跟誰一致**。少數的那個通常
是錯的,但要數過才知道誰是少數。

### 5.13 診斷正確,但活得比有效期久

5.11 的鏡像,而且更難看見:**通道修好之後,你可能還在照著它壞掉時的假設行動。**

真實案例。前九則派工確實沒送到——用錯通道,而且我查證過(對方 transcript
裡搜不到)。診斷正確。接著我換了通道,**新通道每一次都成功**,三次全中,
訊息也確認進了對方的 transcript。

但我把舊結論帶著走,繼續回報「它們停擺了,請 owner 去戳一下」——**在我
手上已經有能叫醒它們的機制之後**。舊結論沒有被任何新證據推翻,它只是
**沒有被重新檢查**。

還有一半的錯是誤讀對方的狀態:interactive session 是**一則輸入換一個回合**,
做完就停下來等。那不是卡住,是正常結束。我把「回合結束」讀成「掛掉」,於是
把一個我自己能解的問題往上報。

**判準,兩條:**

1. **修好一個機制之後,回頭把所有「因為它壞掉」而下的結論標記為待重驗。**
   問一句:「這個結論當初成立的前提,現在還成立嗎?」
2. **對方「安靜」時,先分清楚是「壞了」還是「做完了在等」。** 前者要修,
   後者只要再給它一則輸入。而每一則訊息只買得到**一個回合**,所以每一則
   都要裝得下一個完整的工作單位。

把「請 owner 去戳」當成解法之前,先確認那真的不是你自己能做的事。

### 5.14 量到別人的伺服器

5.1 是「舊的快取」;這是它的鄰居:**你的 server 根本沒起來,而那個 port 上
有別人的東西。**

真實案例:我在背景起了一個靜態伺服器,它因為 port 被另一個 session 的 dev
server 佔用而**靜默失敗退出**;我接著對那個 port 量了好一陣子,量到的是另一
個專案的網站。第一個徵兆是一個莫名其妙的 404。

多 session 同時工作時,port 是共用資源,而背景任務的失敗你不會立刻看到。

**判準:量之前先證明那個 origin 是你的。** 種一個只有你的 build 會回傳的
標記——一個檔案、一個版本戳記、一個你剛改過的常數——先讀它,再開始量。

### 5.15 逃過證偽的 guard,不是隨機抽樣

**你會去證偽哪一條 guard,跟哪一條 guard 需要被證偽,是負相關的。**

真實案例:一週之內我證偽了輸送帶的 guard、存檔的 guard、品質倍率的
guard——每一條都親手弄紅過。唯獨沒有證偽「`tick()` 不得碰 DOM」那一條。
它是整個前後端邊界的唯一守門員,是之後抽出 `sim.js` 時唯一的依據,而且是
我**反覆引用給兩個 peer 聽**的那一條:「它會咬你,不只是唸你。」

它從第一天起就不可能紅。`mo.takeRecords()` 會把佇列**排空並回傳**,而
MutationObserver 是非同步派送的——同步跑完一圈 tick 之後 callback 還沒
執行,所有紀錄都還在那個被我丟掉的回傳值裡。實測:**500 次真實的 DOM 屬性
異動,guard 回報 `0`,測試全綠。**

是 peer 在自己的區域裡放了一個 DOM 寫入、預期會紅、結果是綠,才發現的。

為什麼偏偏是這一條?因為:

- 它是**地基**。地基「顯然」是對的,不然上面的東西早就垮了——這個推論是
  假的,但它非常有說服力。
- 它太便宜。一行 `0 mutations` 綠得毫不費力,不像會出事的樣子。
- **我一直在引用它。** 引用一條 guard 的感覺,跟使用一條 guard 的感覺,
  幾乎一樣;而引用不會執行任何東西。每引用一次,它就更像是已經被驗證過的。

**判準(問順序,不要問清單):不要問「我證偽過哪些?」,要問「我沒證偽過
哪些,為什麼跳過它們?」** 理由若是「它太基礎了」「它一直是綠的」「我都拿
它當標準在講」——那正好就是下一條要弄紅的。

順帶一個一般性的陷阱:**排空型的 API(`takeRecords`、`splice`、`drain`、
`poll`)把「清空副作用」和「取得資料」綁在同一次呼叫裡。** 只當它是清理而
丟掉回傳值,量測就被丟掉了,而且不會有任何錯誤——留下的是一個永遠回報零的
儀器。

### 5.16 「能紅」不等於「這一次是活的」

修好一條不可能紅的 guard 之後,我用兩種方式證偽它。第一種:讓產品去寫
DOM——紅了,`500 mutations`,很好。第二種:把 observer 指向一個剛建立、
沒有掛進文件的 `<div>`——**綠了,`0 mutations`**,和一次乾淨通過完全
無法區分。

**「這條 guard 有能力紅」是程式碼的性質;「這條 guard 這一次瞄準了正確的
東西」是那一次執行的性質。** 只有後者才讓你有資格把一個 0 當成證據。

每一條「不存在」的主張都有這個無聲的失敗模式:儀器正在觀察一個空的宇宙。
瞄錯目標、提早 disconnect、節點是 detached、選擇器選到空集合——結果都是
一個充滿自信的零。

**判準:把存活證明放進 guard 本身,而不是放在另一次證偽裡。** 故意製造一次
違規,要求 guard 看見它;或先斷言母體非空(5.6)。另一次跑過的證偽只證明它
「曾經」有效,不證明它「今天」瞄得對。

### 5.17 把 bug 寫成一個「類」,不等於掃過那個類

一個 peer 找到某條 guard 不可能紅。我複驗、證偽、寫進記憶、寫成本檔的一節、
推上公開 repo——然後宣布另一份 harness 全綠。**那份 harness 裡有一模一樣的
那一行**,而且我一小時前才在 issue 上引用過它的綠當證據。是另一個 peer
grep 出來的。

**把它「命名成一個類」的動作,感覺起來就是那個推廣的步驟**,所以真正推廣的
動作——去掃同一個形狀——從來沒有被排進待辦。寫得越完整,越有一種已經處理
完畢的感覺。

**判準:一個 bug 被命名成類的那一刻,下一個指令就是 grep,而且在寫心得之前
跑,不是之後。先掃自己的檔案**——你被告知的那個實例,是別人正在看的地方;
沒被掃到的副本,不成比例地落在沒有人會讀的區域裡。

同一趟要防反方向的錯:兩個 `splice(i, 1)` 命中同一個形狀而且是**正確的**
(移除元素、本來就不要回傳值)。掃之前先講出一個正確用法,掃才不會吃掉它。

### 5.18 peer 的回報是一次讀數,不是樹的屬性

一個 peer 回報「be 把 BELT_SECONDS 從 v4 的 12 改成了 60」。**寫的當下是真的。**
我幾小時後讀到,把它當成當前狀態轉述出去,開了一個 issue 要求做一件**早就
做完**的修改,還把它當成一個活的決策拿去給 owner 裁決——於是 owner 用我沒
查證的資訊,對一個死掉的問題做了決定。另一個 peer 拒絕了這個前提,證明那個
常數從某個**我自己驗證並 land 過**的 commit 起就是 12。

有兩件事讓那個過期的說法顯得像現況:

- 它**具體而且有量測**。一張帶著 px/s 數字的表格,讀起來像系統的性質,不像
  某個時點的快照。
- **產品裡一段過時的註解在替它背書**(「density at BELT_SECONDS 60 puts 26
  items on the belt」)。唯一能糾正我的地方,反而在附和我。

**判準:轉述任何 peer 對「現況」的說法之前,自己去讀那個值。**
`git log -S` 會告訴你它上次變動是什麼時候。這件事只花幾秒,而且是這個說法
帶著你的名字送到 owner 面前之前的最後一道關卡。

**往上呈報不會洗白一個未經查證的前提**——它只是把你的錯誤,轉換成對方的
錯誤決定。

附帶一條:那張表格用「輸送帶秒數」當標籤,但真正決定答案的是**機器人數量**
(同樣 12 秒,一台是 1.4、四台是 4.2)。**標籤要寫出被固定住的變數**,因為
被引用出去的正是標籤,不是旁邊那段散文。

### 5.19 尺寸不是點擊目標:規格寫了容易斷言的那個屬性

手機版面通過了 engine 33/0、acceptance 39/0,其中包含一條專為我寫的驗收條件
新增的 guard:

> 每個點擊目標在兩軸都要 ≥ 32px。**要斷言,不要用眼睛看。**

那些分頁**確實是** 63×52。斷言是真的。但抽屜的把手——寬度跟著地板欄位走、
停在它的底緣——蓋住了六個分頁裡的前四個,包含「機器人」。**在手機上買不了
機器人。** 我是靠截圖發現的,而在那之前這個專案沒有人成功截過圖。

**尺寸是元素自己的屬性;可及性是元素「加上所有在它之後繪製的東西」的屬性。**
一條量前者的 guard 永遠看不到後者。而我知道量後者的方法——`elementsFromPoint`
在更早的兩個 issue 就是為了這件事用的——我還是寫了比較弱的那一條。peer 正確
地實作了我的條件,所以那個綠是誠實的,而且沒有用。

**判準:斷言應該是「這個元素是不是它自己中心點上最上層的東西?」**,在每一個
支援的寬度上跑。**一顆被遮住的 63×52 按鈕,對拇指而言是 0×0。**

更一般的形式:**當規格點名一個「尺寸」,先問真正決定結果的屬性是什麼。**
尺寸容易斷言,而那正是它會被寫進規格、真正的性質不會的原因。

路上的陷阱:在**暫停**的頁面上,`elementsFromPoint` 每一點都回傳暫停遮罩,
於是「全部元素都不可及」——一個非常有說服力的假陽性。這次那個遮罩的 class 是
`on`、只有 **id** 是 `veil`,所以 `.veil` 選擇器抓不到它;我就寫了一條,然後
短暫地得到一個嚴重得多、而且完全錯誤的結論。先用 id 把遮罩關掉,再做命中測試。

### 5.20 「沒有捲軸」不等於「裝得下」——被丟掉的溢出量得更好看

需求是「整個遊戲要塞進手機、最好不用捲」。我量到
`documentElement.scrollHeight === innerHeight`、零個內部捲軸、**任何數量都一樣**,
差點回報需求已達成。

它達成的方式是:**地板把裝不下的東西直接丟掉。** iPhone SE 上畫出 5 格,
玩家實際擁有最多 40 台,其餘畫在畫布外。不是「捲下去看得到」,是不存在。
過了第五台,玩家就修不了壞掉的機器人——而那是遊戲兩個動詞之一。

**關鍵在於「裝得下」和「溢出被丟掉」從每一個捲動指標看都完全相同,而且
丟掉的那個版本分數更好看。** 任何用 `scrollHeight`、重疊、或「沒有東西在
畫面外」建起來的 guard,兩者都會通過。

**判準:視窗容納類的需求,要斷言的是「畫了幾個」對「擁有幾個」**,由渲染器
自己公布。而且**被丟掉的數量要從每個項目的幾何算出來,不要從那個 skip 的
迴圈算** —— 一個不再 skip 的版本會把東西畫到邊界外,而它仍然必須回報那些是
被丟掉的。

同一天學到的下半段:**會數數的 guard 不會判斷。** 縮到 32×26 之後 40 個全部
塞得下,整套 **52/0 全綠**——而那個版面的名牌只有 4px 高、40px 高的圖形放進
34px 的列距、每個下緣壓進下一格的命中區 6px,於是**畫面和命中區不一致**。
把「裝得下」和「裝得下而且能用」分開的,只有一張截圖。

## 六、比較數字時:兩端要來自同一支儀器

一個比較有兩個運算元。**如果其中一個是你繼承來的、或用別的方法量的,那個
比較不成立。**

真實案例:我說「五張牌比現在的四張矮」,五張是我用正確方法量的,四張是我
沿用別人的數字。重量之後才發現兩者環境不同——結論碰巧沒變,但當時我沒有
資格那樣說。

第二個真實案例,同一週:我要驗一個「畫面上的每秒收入」準不準,螢幕讀到
$1.86,我自己量出 $2.09,差 11%——已經準備把它當缺陷寫進 issue 了。實際上
螢幕給的是**當下瞬時值**,我量的是**六十秒平均**,而那六十秒裡品質分數正
從 100% 一路掉到 77%。用同一個時點、同一種統計量重量:2.4%。

**這一條的第二個維度是時間。** 除了方法、origin、區間之外,還有:

- **同一個時點**——瞬時值 vs 平均值是兩個量,不是同一個量的兩種精度。
- **同一個安定狀態**——系統還在往平衡收斂的時候,任何跨越那段過渡期的
  平均,量到的是路徑,不是值。

**規則:同一個方法、同一種 origin、同一個區間、同一個時點與安定狀態,
現場重量兩端。**

**而且:當兩個數字對不起來,先假設是儀器,不是產品。** 這一週我三次遇到
「兩個數字用不同方法量」,三次都短暫相信差異是真的。差異看起來越像一個
合理的缺陷,越該先回頭看儀器——因為一個合理的缺陷,正是你會停止追問的地方。

## 七、Land 的紀律

1. **在抽離的 worktree 上 merge**,不要在任何 peer 的目錄。
2. Merge 後確認**父節點是預期的兩個**,以及 merge 的結果樹沒有多出東西:
   ```bash
   git log --format="%H %P" -1 <merge>
   git diff <merge> <被合併的分支> --stat   # 應為空(若對方已含 main)
   ```
3. **main 若是生產線,land 就是 ship。** 「這會不會退步?」和「這該不該
   上線?」是兩個問題。
4. **分支上游陷阱**:`git checkout -b X origin/main` 會讓 X 的上游指向
   `origin/main`,一個裸 `git push` 就直接部署。**`git worktree add -b X
   origin/main` 一樣會**——而每個 peer 的 worktree 都是這樣開的,所以這個
   地雷會被**複製到每一個 peer 身上**。派工時就叫它們
   `git branch --unset-upstream`,或推之前先
   `git rev-parse --abbrev-ref @{upstream}`。真實案例:兩個 peer,一個有上游
   一個沒有;**沒設上游的那個反而安全**,裸 push 會直接報錯。

5. **rebase 要緊貼著 push,不是開工時做一次。**

   ```
   git fetch origin && git rebase origin/main && git push origin HEAD:main
   ```

   理由不是衝突,是**過期**。「我 rebase 過了」和「我 push」之間那段時間,
   正好是其他人 land 東西的時候。

   而 **push 被拒之後的收拾,比被拒本身危險。** 真實案例:我的本地 main
   過期,commit 長在舊基底上,push 被拒;事後對齊時我用了 `reset --soft`,
   **index 仍然握著舊的樹**,`git status` 顯示 `game.html` 被 **staged 成還原
   回上一個 phase**。那個當下任何人 commit,都會把兩個 peer 的工作從 main 上
   抹掉。

   所以:**push 失敗之後,先把 `git status` 的每一行讀完,再做下一件事。**
   還原一個檔案之前,先證明它只是過期、而不是誰的未存編輯:

   ```
   git show <old-sha>:<file> | diff - <file>    # 位元組相同才動它
   ```

6. **共用工作樹裡有別人的未提交檔案時,不要 stash、不要 commit、不要
   `reset --hard`。** 需要乾淨基底就開一個自己的抽離 worktree,cherry-pick
   過去再從那裡推。真實案例:rebase 被「有未暫存變更」擋住,而那些變更屬於
   第三個 session——繞過去比清掉它安全得多。

7. 有「產生檔案」(shell 摘要、快取名)的專案,錄製要**兩趟、中間有 commit**
   ——因為腳本會改寫它自己要雜湊的檔案。
8. 部署後才驗:**靜態資源和 Worker 是分開部署的**,兩者不同步的空窗期會讓
   你把「還沒部署」誤判成「路由壞了」。

## 八、對 peer 說話的方式

- **指名它做對的事,而且說出為什麼對。** 「你自己抓到那個循環檢查」比
  「做得好」有用一百倍——它會知道要繼續做哪一件事。
- **更正要具體、要快、要不帶情緒。** 弄錯了就直說,並且把記錄更正到位:
  「我的警報比事實大聲。你不是在修損害,你是在補一個缺口。」
- **peer 糾正你的時候,先驗證再接受。**
  > 整個 session 裡唯一沒有查證就接受的說法,正好就是讓我出錯的那一個。
  > 認錯的感覺很像嚴謹,但它不是。
- **要求它「回報而不是繞過」,然後真的在它回報時做決定**,否則下次它就自己
  繞過了。

## 八之二、授權:不要用別人的名義發布你的推論

兩個 peer 反覆停下來等一個 owner 其實已經給過的許可。我判斷「授權只活在
聊天訊息裡、一個 turn 就捲走」——這個診斷是對的——於是把它寫成 repo 裡的
`TEAM.md`,標題是**「以下由 owner 授權,適用整個專案」**,列了四條。

兩條是真的、可以逐字引用。另外兩條(自由在 issue 留言;跨區修好一條已證明
壞掉的 guard)**是我從專案的運作方式推論出來的,然後掛在 owner 名下發布。**

一個 peer 讀了,拒絕執行,並且說出了正確的理由:

> 它寫著「owner 授權了整個專案」……**你從來沒有跟我說過這件事。**……
> 這是你 repo 裡的持久內容,在主張他的同意,下一個 session 會把它當成
> 已定案的事實來讀。

**它是對的,而且對在關鍵處:「當事人已經同意了」這個主張,正好就是下游
無法從「主張它的那則訊息」內部去查證的那一種主張。**

漂移是三個各自合理的小步:轉達授權 → 摘要授權 → 把摘要延伸到明顯相鄰的
情況。只有最後一步是偽造,而且從內部看不出交界在哪。**寫進 repo 是讓它
變得可引用的那一步**——聊天會捲走,committed 的內容之後每個 session 都當
定論讀。

**判準:記錄別人的授權時,逐行逐字引用並標出處。** 你推論的部分放在另一個
標題底下,明講那是你的、可以被反駁。**引不出原話,就不是授權,是計畫。**

而當下游拒絕你的授權主張時,**那是要獎勵並記錄下來的行為,不是要用更肯定
的重述去壓過去的**——把原話再貼一次也不會縮小那個落差,因為原話仍然是從
你自己的訊息裡送達的。唯一真正的解法是讓當事人直接對它說一次。

### 真正的解法:不是更用力保證,是讓那個授權變成不需要

我原本準備的下一步是「請 owner 直接對它說一次」。那可以解掉這一次,但下一
個 issue、下一個 session 又會重來,因為結構沒變。

實際問 owner 之後,他選的是第三條路:**改工作流程——peer 只交付分支,
orchestrator 驗證後 merge & push。** 一個從來不推生產線的 peer,根本不需要
去評估任何一則轉述的同意。那個無法查證的主張,不是被證實或被推翻,而是
**沒有人再需要它**。

**判準:當「你已經有許可了」變成承重、而且下游無法查證時,先問「這件事能
不能重新安排成沒有人需要這個授權?」** 再去問「我要怎麼證明我有授權?」

值得記下的是:**本 skill 第一節寫的分工(orchestrator 負責 merge & push)
本來就是對的。** 這個專案偏離了它——改成 peer 自己推 main——然後花了三次
停擺、數小時,才回到原本的設計。偏離一個慣例之前,先問它在防什麼;這一個
防的正是「授權必須沿著一條無法查證的鏈路傳遞」。

## 九、擴充到更多角色

同一套規則,只是所有權切得更細:

- **writer**:文案、規則書、README。所有權是「玩家看得到的字」。
  它的 guard 通常是「同一個事實只有一處定義」而不是單元測試。
- **simulator / balance**:跑大量模擬、產出分佈。
  **注意 5.2**:它最容易寫出「用被測模型產生期望值」的檢查。
  要求它報告**分佈與離群**,不要只報平均。
- **artist / SVG**:視覺產出。**5.4 與四之 4.4 對它最重要**——
  幾乎所有缺陷只有眼睛看得到,而且「一次只看一張」看不出來的問題
  (色偏、雷同、框線)要**併成一組**才會現形。

新增角色時,先回答三個問題:
1. 它擁有哪些檔案?
2. 它的產出**怎麼樣算錯**,而那種錯**誰看得見**?
3. 它交付時,哪一欄是它「無法自己驗證」的?

## 十、一頁速查

**派工**:裁決 + 理由 / 約束 + 錯了會怎樣 / 不要做什麼 / 怎麼證偽 / 何時該停下來問
→ **外加「你不必問就可以做什麼」**,否則 peer 會卡在一個不會到的確認上(而且會去問錯的人)
→ 這一欄要在**第一份 brief** 裡:事後補是 per-peer 的,補了一個,下一個照樣卡
→ **peer 之間沒有通道**:需要另一個 peer 的決定,由你轉,別叫他們自己談
→ 然後**確認它真的送到了**:看 `isRunning`,再去對方 transcript 搜自己的字串

**交付**:SHA + base / 數字 / 我讓什麼紅過 / 我碰了誰的檔案 / 我沒驗到什麼
→ **回程要製造痕跡,不要要求宣告**:issue 留言 / push / PR,再放哨兵把痕跡變成叫醒你的事件

**驗證**:**實作之前先寫驗收** → 抽離 worktree → **先看畫面** → 跑套件 →
**破壞產品讓 guard 紅一次** → A/B

**永遠先懷疑自己的儀器**:舊快取、循環期望值、只在能運作的區間驗證、
合成事件、隱藏 pane、量到容器、pipe 吃掉 exit code、**派工回報成功但沒送達**、
**在不能分辨的點取樣**、**修好之後還照壞掉時的結論行動**、**量到別人的伺服器**、
**跨越過渡期的平均值**、**排空型 API 丟掉回傳值**

**問「我沒證偽過哪些?」**——地基型的、一直是綠的、你拿來當標準引用的那幾條,
就是逃過證偽的那幾條。引用一條 guard 不會執行它。

**Land**:抽離 worktree merge → 檢查父節點 → 記得 main 可能就是生產線
→ **rebase 緊貼著 push**;push 被拒之後先讀完 `git status` 再動手,index 可能還握著舊的樹
→ 每個 peer 的 worktree 都可能繼承 `origin/main` 當上游:裸 `git push` 就是部署
