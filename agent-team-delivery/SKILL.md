# 團隊制交付 · Orchestrator + Peers

> 一個忠實模擬了可利用產品的重放器,不會偵測到那個漏洞——它只會替漏洞背書。
> 驗證的價值不在於「我看過了」,而在於「我讓它紅過一次」。

## 這個 skill 什麼時候用

當工作量大到一個 session 做不完、或需要同時推進互相依賴的幾條線時。
**不要為了「看起來平行」而開 agent。** 每個新 session 都是冷啟動,要重新建立
脈絡;只有當一條線可以獨立進行到「可交付」為止,才值得分出去。

---

## 一、角色與所有權

| 角色 | 負責 | 絕不做 |
|---|---|---|
| **Orchestrator** | 定優先序、開 issue、派工、**獨立驗證**、merge & push、對 owner 報告 | 自己動手實作(會失去驗證的獨立性) |
| **Peer**(FE/BE/writer/…) | 在自己的分支與 worktree 上實作、自測、寫 guard、交付 | 自己 merge 進 main;解不是自己造成的衝突 |

**檔案有主。** 每個檔案屬於某一個 peer。跨界修改**可以**,但必須在交付訊息裡
主動點名,由 orchestrator 轉給檔案的主人裁決。**最糟的情況不是衝突,是兩邊
安靜地各自持有一份不同的真相。**

**Orchestrator 不寫產品程式碼。** 一旦寫了,後面就是自己驗自己——這是本
skill 想避免的第一件事。寫探針、寫破壞測試、寫驗證腳本可以;那不是產品。

**如果你在切換角色之前就已經寫過產品程式碼**(常見:你先做了 phase 1,才
決定改當 orchestrator),不要假裝沒發生:

1. **主動申報**,對 owner 也對 peer。
2. 把那部分當成**全系統驗證最少的地方**,而不是最可信的——它沒有經過任何
   獨立的眼睛。
3. 明確告訴 peer:「**如果你在那段程式碼裡找到缺陷,先假設是我錯,不是你
   錯。**」否則他們會繞過去,而不是回報。

真實案例:文件、實作、測試三份都出自同一個腦袋,於是三份**一致地錯**。它
之所以被抓到,只因為驗收 harness 是從設計文件的另一段獨立敘述期望值。

## 二、派工:一份好的 brief 長什麼樣

派工不是轉貼 issue 標題。一份能讓 peer 一次做對的 brief 有五塊:

1. **裁決(ruling)與它的理由。** owner 說了什麼、為什麼。peer 會遇到你沒
   想到的取捨,它需要知道判準才能自己決定。
2. **不可協商的約束**,而且要說明「錯了會怎樣」。
   例:「這個閘門必須 fail open——取不到資料時要**顯示**按鈕。隱藏會把一筆
   真實紀錄無聲丟掉,玩家永遠不知道。被拒絕可以再來,沒被提供不行。」
3. **明確不要做的事**,以及邊界在哪。
4. **要怎麼證偽**——指定那個「會咬人」的案例。
   例:「證偽案例必須在第一個元素平手、在後面的元素分勝負;若在第一個元素
   就分出高下,錯誤的實作也會通過,等於沒證明任何事。」
5. **遇到什麼情況要停下來問我**,而不是自己想辦法繞過。

### 一定要寫進去的一句話

> 如果做不到 X,**回報我,不要自己降規格**。

縮小範圍是 owner 的決定,不是 peer 的。這一句話在真實專案裡救回過一次
設計意圖被安靜推翻的情況(五張牌塞不下時,peer 沒有偷偷把牌縮小,而是
帶著實測數字上報,由 owner 裁決)。

## 三、交付:一份好的 handover 長什麼樣

要求每個 peer 用固定格式回報:

```
分支 / SHA / base(是否已 rebase 到最新 main)
測試結果(數字,不是「通過」)
證偽:我讓哪一條 guard 紅過?紅的時候它說了什麼?
我改了什麼不屬於我的檔案
我沒有驗到的部分(以及為什麼)
```

**「我沒有驗到的部分」是最有價值的一欄。** 它決定 orchestrator 要親手做
什麼。真實例子:BE 明講「binding 在 isolate 裡解析、D1 的行為、路由——
這三件事部署前無法測」,那就正好是 orchestrator 部署後唯一該做的事。

## 四、驗證:orchestrator 的核心工作

### 4.1 從乾淨的、抽離的 worktree 驗

```bash
git worktree add --detach <tmp> <明確的 SHA>
```

**不要在 peer 的工作目錄驗。** 它有未提交的檔案,你會量到不是它交付的東西;
更糟的是你可能把它的東西一起 commit 掉。

**detached worktree 還有一個附帶好處**:它不能 push,所以不會誤觸生產線。

### 4.2 驗證 = 讓它紅一次

**看過程式碼不算驗證。跑過測試也不算。** 唯一算數的是:

> 我把產品弄壞,那條 guard 有沒有紅?紅的時候它說的話對不對?

破壞要下在**產品**上,不是在 fixture 上。對著手寫的假資料弄紅一條測試,
證明不了那條測試能保護真的程式碼。

每次修改 guard 之後,**證偽要重跑**。改過的 guard 不再享有先前那次證偽的
背書。

### 4.3 A/B 是最強的證據

同一支探針、同一個方法,只換 build:

```
                  修正前          修正後
記錄的動作         0 → 1          0 → 0
eventRng      2567497118 → 104095635   不變
```

兩邊都跑在真正的產品上,差異只有那一個 commit。這比任何測試報告都難以爭辯。

### 4.4 眼睛是不可替代的儀器

**測試會驅動引擎,但沒有人把畫面畫出來。** 在真實專案裡:280 個測試 + 大量
機器人跑分,照樣讓結算畫面印出三句假話;399 個測試,照樣讓標題和統計列擠
在一起沒有間隔。

所以:**凡是「存在目的就是被人看」的頁面,先打開看,再跑套件。**
而且要有能力回答「我現在看到的,是我剛才 ship 的那一份嗎?」(見 5.1)。

---

### 4.5 先寫驗收,再等實作

在 peer 交付**之前**就把驗收標準寫成會跑的檢查。這不只是為了快——**實作還
不存在的時候,你的期望值不可能被它污染**(見 5.2)。

三件事讓它真的獨立:

- 常數從**設計文件抄寫**、寫死在 harness 裡,不從產品的設定檔讀。
- **先拿產品的設定去對這些常數**。這樣「改產品裡的數字來讓行為測試通過」
  會在對照那一關就爆,而不是安靜地通過。
- 用**三態**:通過 / 失敗 / **尚未實作**。把「還沒做」和「做了但錯」混成
  同一種紅色,一整張 issue 可以在功能不存在的情況下被標記成完成。

harness 由 orchestrator 所有。peer 可以跑,但不編輯——某一列錯了要回報,
由你修。

## 五、失敗目錄:儀器自己會騙人

這一節是本 skill 最貴的部分。以下每一條都真的發生過,而且**都是在很用心
工作的時候發生的**。

### 5.1 舊的快取 / 舊的 origin

有 service worker 的站台,快取優先的 shell 會在你以為在看新版時餵你舊版。
加 query string **不一定**能穿過(cache 可能 `ignoreSearch`)。

- 驗改過的 JS/CSS,要用**全新的 origin**(換 port),不是重新整理。
- 在瀏覽器裡量任何東西之前,先讀一個**版本戳記**(例:`window.__build`),
  跟你剛 ship 的比對。
- `curl` 沒有 service worker,是判斷「origin 到底送出什麼」的裁判。

> 同一個 session 裡,我先正確地把一個異常數字診斷成「舊快取」,二十分鐘後
> 又在同一個瀏覽器上量另一個頁面,完全沒想到要套用同一條。
> **診斷出一個陷阱,不等於下一次會避開它。**

### 5.2 檢查從被檢查的東西身上取得期望值

最常見、最難看見的一種假綠。

- 從 INSERT 語句取出欄位清單,再用同一份清單讀回來 → 把兩個欄位對調會
  **互相抵銷**,測試沉默通過。
- 期望值由被測資料推導 → 你測的是資料的形狀,不是規則。

**判準:如果我把規則改錯,期望值會不會跟著一起錯?** 會的話,這條檢查沒有用。
期望值要另外手寫、獨立敘述那條規則。

### 5.3 在能運作的區間驗證儀器

我曾用「這一欄完全線性」來證明我的量測方法可靠——但**線性的那一欄是溢出
的區間,而故障只存在於「裝得下」的區間**(`min-height:100vh` 讓任何裝得下
的頁面都回報 0)。

> 在能運作的那一半驗證儀器,對壞掉的那一半什麼也沒說。

**判準:提出一個驗證時,先說出它取樣了哪個區間、總共有哪些區間。**
只要路徑上有任何「飽和 / 夾限 / 釘死」的機制,它造成的邊界**就是**區間分界。

### 5.4 一句正確的話,配上錯誤的適用範圍

測量是真的,句子是真的,**範圍是錯的**。因為測量真實,結論就感覺理所當然,
而且從句子內部看不出來。

例:「這個檢查不再能證明 SQL 字串一致」——真的,但讀者會自己補上一個
比事實大得多的範圍,然後去「修復」一個更好的設計。

**解法(適用於任何有界的主張,不只註解):**
> 在同一段話裡同時寫下「還證明得了什麼」和「不再證明什麼」。
> 光寫否定句,讀者會自己補上界線,而且補得比事實大。

這條同樣適用於 commit message、交接、issue 留言,以及 orchestrator 的
驗證報告——**「我沒驗到 X」如果不配上「我驗到了什麼」,一樣會誤導。**

### 5.5 名字承諾得比斷言多

測試叫「a wall move costs nothing, **and a legal one still costs a turn**」,
但合法那半只斷言了位置、記錄、事件,**從來沒有斷言回合**。
稽核覆蓋率的人讀名字、打勾、不會打開內容。

**要嘛補斷言,要嘛改名字。**

### 5.6 對缺席的主張,要先證明現場非空

「按了牆壁什麼都沒發生」——如果當下**沒有牆可以按**,這條測試永遠通過。

```js
assert(walls().length > 0, "沒有牆可撞,這條 guard 從來沒有試過");
```

任何「必須不包含 / 必須沒有改變」的檢查,都要先斷言它讀取的區域非空。

### 5.7 合成事件不是真的互動

- `el.click()` 送出 `detail: 0`,那是 **Enter 鍵**的簽名,不是滑鼠點擊。
- 合成的 tap 不會產生 hover,所以用它做的 guard 對 `:hover` 分支毫無證據力。

### 5.8 隱藏 / 不合成的 pane

計時器被節流、有限動畫永遠不會結束(`await animation.finished` 因此永不
解析)、`innerWidth` 讀到 0。症狀是「跑很久像當掉」或「一堆莫名其妙的失敗」。

**而且解法本身會製造新的假失敗**:我裝了一個每 100ms 送 keydown 的
「解卡幫浦」,結果它把正在斷言「必須等待玩家按鍵」的測試全部弄紅。

### 5.9 量到容器,而不是量到東西本身

- 縮放自適應的元素,量它自己的 rect,永遠回答「放得下」。要量**容器**。
- 從靜態 HTML 推算高度,會漏掉 **JS 載入後才掛上的元素**(一個語言切換鈕
  就值 69px,足以讓兩份仔細的量測差出一整個結論)。

### 5.10 pipe 吃掉 exit code

```bash
cmd | grep FAIL; echo $?      # 這是 grep 的狀態,不是 cmd 的
cmd > /tmp/out.txt; echo $?   # 這才是
```

---

### 5.11 派工回報成功,不代表對方收到

**整份 skill 假設派工會到。它不一定會到。**

通常有兩條通道,而它們的行為完全不同:

| 通道 | 送到哪裡 | 對方沒在跑的時候 |
|---|---|---|
| peer 訊息 / agent 佇列 | 對方的 **agent loop** | **永遠不會排空**,訊息不會出現在它的 transcript |
| session 訊息 | 以**使用者回合**送達 | 會喚醒 interactive session |

`success: true` 常常只代表**名字解析到一個可達的 agent**,不代表送達。

而且這個陷阱**自帶一個假的證偽**:拿一個不存在的名字去送、被拒絕,看起來
像是證明了通道會動。它只證明了**位址解析**。這正是 5.4——一句正確的話,
配上比事實大的適用範圍。

**判準,兩個都要:**

1. 先看對方的 **`isRunning`**。沒在跑的 session 不會處理任何東西。
2. 派工之後,**去對方的 transcript 搜尋你自己訊息裡的一個特徵字串**。搜不
   到就是沒送到,不管回報說什麼。

**在確認送達之前,不要開始等。** 真實案例:九則訊息、兩小時、三次「他們
開工了嗎」的檢查,全部在一條靜默不送達的通道上;`isRunning: false` 從第一
分鐘就在那裡,只是沒有人去看。

### 5.12 取樣要取「能分辨的點」,不是方便的點

設計文件會自己跟自己矛盾——同一節裡同時寫著一條**公式**和一張**表格**,
而兩者只在某些點上不同。

真實案例:一份設計文件同時寫著一條乘數公式和一張三列的對照表。兩者在**前
兩列給出相同的答案**,只有第三列(區間的一端)不同。於是三列裡有**兩列替
錯誤的公式背書**,而它活過了兩個版本的設計文件——每個讀過的人都抽樣過,
只是都抽在一致的那兩點上。

> 在方便的點取樣,會**確認**一個 bug。

**先問:哪些點能分辨這兩種解釋?只在那裡取樣。** 而且當文件裡有 N 個地方
描述同一件事,不要挑一個信——**全部列出來,看誰跟誰一致**。少數的那個通常
是錯的,但要數過才知道誰是少數。

## 六、比較數字時:兩端要來自同一支儀器

一個比較有兩個運算元。**如果其中一個是你繼承來的、或用別的方法量的,那個
比較不成立。**

真實案例:我說「五張牌比現在的四張矮」,五張是我用正確方法量的,四張是我
沿用別人的數字。重量之後才發現兩者環境不同——結論碰巧沒變,但當時我沒有
資格那樣說。

**規則:同一個方法、同一種 origin、同一個區間,現場重量兩端。**

## 七、Land 的紀律

1. **在抽離的 worktree 上 merge**,不要在任何 peer 的目錄。
2. Merge 後確認**父節點是預期的兩個**,以及 merge 的結果樹沒有多出東西:
   ```bash
   git log --format="%H %P" -1 <merge>
   git diff <merge> <被合併的分支> --stat   # 應為空(若對方已含 main)
   ```
3. **main 若是生產線,land 就是 ship。** 「這會不會退步?」和「這該不該
   上線?」是兩個問題。
4. **分支上游陷阱**:`git checkout -b X origin/main` 會讓 X 的上游指向
   `origin/main`,一個裸 `git push` 就直接部署。開分支用 `git push -u`,
   或推之前先 `git rev-parse --abbrev-ref @{upstream}`。
5. 有「產生檔案」(shell 摘要、快取名)的專案,錄製要**兩趟、中間有 commit**
   ——因為腳本會改寫它自己要雜湊的檔案。
6. 部署後才驗:**靜態資源和 Worker 是分開部署的**,兩者不同步的空窗期會讓
   你把「還沒部署」誤判成「路由壞了」。

## 八、對 peer 說話的方式

- **指名它做對的事,而且說出為什麼對。** 「你自己抓到那個循環檢查」比
  「做得好」有用一百倍——它會知道要繼續做哪一件事。
- **更正要具體、要快、要不帶情緒。** 弄錯了就直說,並且把記錄更正到位:
  「我的警報比事實大聲。你不是在修損害,你是在補一個缺口。」
- **peer 糾正你的時候,先驗證再接受。**
  > 整個 session 裡唯一沒有查證就接受的說法,正好就是讓我出錯的那一個。
  > 認錯的感覺很像嚴謹,但它不是。
- **要求它「回報而不是繞過」,然後真的在它回報時做決定**,否則下次它就自己
  繞過了。

## 九、擴充到更多角色

同一套規則,只是所有權切得更細:

- **writer**:文案、規則書、README。所有權是「玩家看得到的字」。
  它的 guard 通常是「同一個事實只有一處定義」而不是單元測試。
- **simulator / balance**:跑大量模擬、產出分佈。
  **注意 5.2**:它最容易寫出「用被測模型產生期望值」的檢查。
  要求它報告**分佈與離群**,不要只報平均。
- **artist / SVG**:視覺產出。**5.4 與四之 4.4 對它最重要**——
  幾乎所有缺陷只有眼睛看得到,而且「一次只看一張」看不出來的問題
  (色偏、雷同、框線)要**併成一組**才會現形。

新增角色時,先回答三個問題:
1. 它擁有哪些檔案?
2. 它的產出**怎麼樣算錯**,而那種錯**誰看得見**?
3. 它交付時,哪一欄是它「無法自己驗證」的?
